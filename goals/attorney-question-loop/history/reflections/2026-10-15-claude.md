# Reflection — attorney-question-loop (2026-10-15, claude)

## Summary

The goal shipped the loop that lets agents ask the attorney through the review queue instead of
a polled inbox:
- a `question` ReviewItem and the `AnswerRow` (P0, #1801);
- the `QuestionQueue` and `QuestionWrites` contracts and services: validated answers, a daily
  digest, all-or-nothing calendar writes on provisional events, and undo that never overrides the
  attorney (P1–P2);
- the docket-intake producer and the count-only daily notice (P3a);
- the workstation review hub, an HTTP MCP bound to loopback and gated on the tailnet login, with
  four tools and JSONL stores (P3b);
- sample units, the notice job, opt-in docket-intake wiring and a runbook (P3c).

The pane client and the live enable step belong to the review-queue follow-on and the operator.

## Tooling experience

- **Worked:** design documents written before each phase (P0-SCHEMA, P1-CONTRACT, P3B-HUB) let one
  child implement every phase with few deviations, and every deviation was recorded.
- **Didn't:** the Junie lane died on a balance the accounts screen did not show, and one test run
  bypassed the heavy-job queue.
- **Frustrating:** each merge of main conflicted on generated files and the observability
  catalog, as other PRs landed in between. The orchestrator's merge ordering helped.

## Implementation improvement opportunities

- A delete or tombstone for review items.
- Richer docket ledger records, so questions can offer candidate dates.

## Goal & prompt critique

The data plane was missing from the brief. The shape review settled the surface and the write
policy, but not where the logs live when the surface and the jobs run on different machines.

## Lessons (confidence-tiered)

- **HIGH — Critical:** Decide cross-machine data flow before the services are built.
- **MEDIUM — Best practice:** Keep packet edits and code edits in separate commits when a child
  shares the tree, and stage files by name.
- **LOW — Consideration:** Chain PRs that touch the same generated catalogs, so each merge does not
  make the next one DIRTY.
