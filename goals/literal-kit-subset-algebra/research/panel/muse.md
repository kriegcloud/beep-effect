# Literal-domain helper kit over Effect v4 `Schema.Literals` — design evaluation

> Independent review. Sources read directly: current kit, pre-trim kit (`b26ed3a81d^`), upstream `Schema`/`Match`/`Data` declarations in `node_modules/effect`, the 2026-09-15 retirement ruling, the trim codemod, and sampled consumers. File:line citations refer to the working tree unless marked pre-trim.

## Evidence base

- Current kit: `packages/foundation/modeling/schema/src/LiteralKit/LiteralKit.schema.ts` (455 lines). It wraps `S.Literals(literals)` at :412-455 and attaches only `is`, `Enum`, `$match`, `toTaggedUnion` via property descriptors; statics survive derivations by overriding `rebuild` at :304-318 (upstream `annotate`/`check` return `this.rebuild(ast)`).
- Pre-trim kit (`git show b26ed3a81d^:.../LiteralKit.schema.ts`, 835 lines) additionally carried `Options`, `HashSet`, `pickOptions`, `omitOptions`, `thunk`, and a user-supplied `enumMapping` (the `M` type parameter threaded through `EnumType`/`IsGuards`/`MatchFn`/`ToTaggedUnionFn`, pre-trim :57-203), plus three extra error classes for mapping validation (pre-trim :305-455).
- Upstream `Schema.Literals` (`node_modules/effect/dist/Schema.d.ts:4138-4153`) already exposes `literals: L`, `members`, `mapMembers`, `pick(literals): Literals<L2>`, and `transform(to)`. So the tuple and subset-selection facets are genuinely upstream-owned; there is no upstream `omit`, no keyed record, no per-member guards, and no record-form match for bare literals.
- Upstream tagged unions: `Schema.TaggedUnion` (`Schema.d.ts:5263-5309`) and `toTaggedUnion` utils (`Schema.d.ts:5154-5205`) expose `guards` (a record, not `is`), `match`/`matchOrElse`, `cases`, `discriminants`, `isAnyOf` — but keyed by `_tag`/discriminant with struct members, not bare literal values, and `TaggedUnion` hardcodes `tag: "_tag"` (:5285).
- `Data.taggedEnum` (`node_modules/effect/dist/Data.d.ts:358-380`) is the sole upstream precedent for `$is`/`$match` dollar names; Schema's own spelling is `guards`/`match` without `$`.
- 2026-09-15 ruling (`explorations/effect-schema-parity/DECISIONS.md:445-525`): census showed `.Enum` 1,172 lines/227 files, `.is` 603/259, `.$match` 243/143, `.toTaggedUnion` 36/27 against covered facets; retired `Options`/`pickOptions`/`omitOptions`/`HashSet`/`thunk`/`enumMapping`. Codemod at `packages/tooling/tool/cli/src/commands/Lint/internal/SchemaParityCodemodLiteralKitRule.ts:43-68` encodes those rewrites.
- Representative consumer: `apps/labs/ciops/src/kpi/Schemas.ts:48-59` defines `KpiTier = LiteralKit([...]).pipe($I.annoteSchema(...))` — note `.pipe(...)` after construction, which only keeps helpers because of the `rebuild` override; `apps/labs/ciops/src/kpi/Fold.ts:298-313` uses raw `Match.type<...>().pipe(Match.when(...), Match.exhaustive)` over the same domain instead of `KpiTier.$match`, a first hint that `$match` and `Match` are not composing in practice.


## Summary of position

Keep the kit, but stop treating the 2026-10-01 trim as settled. The trim was right about aliases (`Options`, eager `HashSet`, `thunk` as a stored record) and wrong, or at least unproven, about the two facets that express *domain algebra* rather than naming: a typed complement (`omit`) and kit-preserving subset derivation. The correct line is not "upstream covers it" but "upstream covers it *without losing the domain or its invariants*". `Schema.Literals.pick` covers picking values; it does not cover picking a *named sub-domain that still has `Enum`/`is`/`match`*, and the repo proves this by re-wrapping `LiteralKit(X.pick([...]).literals)` at ~11 sites and by hand-spelling a 236-member complement pick in `CitingApplicationIdentity.model.ts:82-318`. My preferred surface is small: keep `literals` (upstream), `Enum`, per-member guards, an exhaustive record match, and `toTaggedUnion`; add kit-preserving `pick`/`omit` that return `LiteralKit`s; make the set and thunks lazy derived views rather than stored facets; drop the `$` from the match (or keep `$match` only for `Data.taggedEnum` parity — I lean rename, below); do not restore the old `enumMapping` `M`-parameter design — `MappedLiteralKit` is the right home for user key mappings. The kit should exist because a named literal domain is a domain type in this codebase, and 600 files are not an accident; but it should be a *thin domain wrapper over* `Schema.Literals`, not a second schema system.

## 1. Which helpers should the kit carry?

Verdicts, facet by facet. "Keep" means the kit owns it; "upstream" means call sites use `Schema.Literals`/Effect directly; "redesign" means the need is real but the trimmed shape was wrong.

| Facet | Verdict | Reason |
| --- | --- | --- |
| Readonly members tuple | **Upstream** (`literals`) | `Schema.Literals` already exposes `readonly literals: L` (`node_modules/effect/dist/Schema.d.ts:4139`). The pre-trim `Options` was a pure alias. No disagreement with the trim here. |
| Typed subset selection (`pick`) | **Redesign — kit-preserving** | Upstream `pick` exists (`Schema.d.ts:4147`) but returns a bare `Literals<L2>`, silently dropping `Enum`/`is`/`match`. Consumers immediately re-wrap: `LiteralKit(EdgeAuthorityOperationBase.pick(["record","supersede"]).literals)` (`packages/epistemic/use-cases/src/EdgeAuthority/EdgeAuthority.errors.ts:72`), same pattern at `HarnessLedger.schemas.ts:86`, `FileTypeChecker.behavior.ts:46`, and ~8 more (`rg "LiteralKit\\([^)]*\\.pick\\("` → 11 hits). A derivation that loses the domain's API is not coverage. The kit should override/wrap so subsets stay kits (see signatures below). |
| Complement (`omit`) | **Restore, redesigned** | This is the trim's weakest call. "Omit is an explicit pick of the complement" (`DECISIONS.md:461`) is exactly backwards for maintenance: the complement is the thing that changes when the domain grows. The repo now contains a 236-line hand-spelled complement (`CitingApplicationIdentity.model.ts:82-318`, comment at :80 literally says "spelled out as the complement pick") with an explicit element type to stop TS inferring a 238-member tuple. That file is the counterexample. `omit` should be computed from the parent tuple so adding a member to the parent automatically flows into the complement, and the empty-complement case should be a *type* error, not the pre-trim runtime `LiteralNotInSetError` throw (pre-trim :554-579, :305-315). |
| `HashSet` of members | **Drop as stored facet; offer lazy derived** | The trim's stated reason — "also stops building a HashSet for every kit" (`DECISIONS.md:472-473`) — is sound for the common case where the set is never touched. But `HashSet.fromIterable(X.literals)` now appears at real call sites, repeatedly rebuilt inside functions in tests (`LegalPositionRelatorPolicy.test.ts:196,228-244`). A lazy memoised getter costs nothing when unused and gives one canonical instance when used. If forced to choose keep-vs-drop with no lazy option, I drop it: membership tests on ≤ a few dozen literals do not need a prebuilt set. |
| Record of zero-arg thunks | **Drop as stored facet** | `Function.constant(Kit.Enum.k)` covers it (census: 65 lines/15 files, `DECISIONS.md:460`), and the codebase already writes `F.constant(ThemeMode.Enum.system)` (`apps/professional-desktop/src/theme/Theme.atoms.ts:39`). A stored thunk record is one closure per member per kit for a need that is already one partial application away. No disagreement with the trim. |
| Record of members keyed by name (`Enum`) | **Keep — this is the kit's raison d'être** | 1,172 lines/227 files in the 2026-09-15 census (`DECISIONS.md:456`); nothing upstream is keyed by literal. It is also the safest way to reference a member: `Status.Enum.number1` fails at compile time on a typo or rename in a way a bare `"hello"` string does not. Keep the name `Enum` despite the collision with TS `enum` — the census shows the repo reads it fluently. |
| Per-member type guards (`is`) | **Keep** | 603 lines/259 files (`DECISIONS.md:457`). Upstream offers only `S.is(schema)` for the whole union or index-based member schemas. Per-member guards keyed the same way as `Enum` are what make `if (Status.is.hello(x))` narrow without a cast. One guard per member is `O(1)` closures and trivially derived. Keep. |
| Record-form match | **Keep, exhaustive (see §3)** | 243 lines/143 files (`DECISIONS.md:459`); upstream `Match` has `valueTags`/`tags` only for `_tag`-discriminated objects (`node_modules/effect/dist/Match.d.ts:390-457`, `:1073-1115`), not bare literals. This is the facet with no upstream analogue at all. |
| Conversion to a tagged union | **Keep** | All 27 pre-trim sites used a custom tag; upstream `Schema.TaggedUnion` hardcodes `tag: "_tag"` (`Schema.d.ts:5285`) and `S.toTaggedUnion(tag)` (`Schema.d.ts:5253-5255`) needs hand-written structs. The kit's version derives the structs from the literal domain so coverage cannot drift. The typeperf fixture (`test/fixtures/typeperf/literal-kit-tagged-union.ts:1-3`) shows the repo already benchmarks it against upstream's tagged-union fixture — keep it, it is pulling its weight (355 `toTaggedUnion(` hits repo-wide today). |
| User-supplied key mapping (`enumMapping`) | **Drop from `LiteralKit`; `MappedLiteralKit` owns mappings** | The trim's "one measurable type-check win" (`DECISIONS.md:477-480`) is credible: the `M` parameter threaded through every helper type (pre-trim :63-203) plus three validation error classes (pre-trim :305-455) bought key renaming at 12 sites/4 files. Key mapping is a *mapping between two domains*, and the repo already has the right concept for that: `MappedLiteralKit` with `From`/`To` kits (`MappedLiteralKit.schema.ts:75-82,292-296`). I would rather see the two ex-`enumMapping` consumers express the rename as a `MappedLiteralKit` or a plain local `Record` than re-thread `M` through the base kit. |

**Where the line sits.** A facet belongs to the kit iff removing it forces consumers to either (a) lose the domain's keyed/exhaustive API, (b) hand-maintain a derived artefact that must stay in sync with the literal tuple, or (c) re-derive the same value at many call sites with no canonical instance. By that test: `Options` fails (a rename, not a loss), stored `HashSet`/`thunk` fail (one-liner derivations, canonical instance optional), `enumMapping` fails (a mapping, not a domain facet). Kit-preserving `pick`, `omit`, `Enum`, `is`, record match and `toTaggedUnion` pass. The doctrine's test — "public upstream API covers what consumers use it for" (`standards/architecture/DECISIONS.md:2040-2045`) — is subtly wrong as stated: `pick` "covers" subset selection the way a function that returns an unkeyed array "covers" a keyed record. Coverage should be judged on the *result type consumers actually program against*, including whether the domain's invariants and helpers survive.

Proposed subset algebra (types only; runtime is a filter):

```ts
interface LiteralKit<L extends Literals> extends S.Literals<L> {
  // ... Enum / is / match / toTaggedUnion as §2 ...
  pick<const P extends NonEmptyReadonlyArray<L[number]>>(picked: P): LiteralKit<P>
  omit<const O extends NonEmptyReadonlyArray<L[number]>>(
    omitted: O
  ): [Exclude<L[number], O[number]>] extends [never]
    ? "omit would empty the domain" // or a never-typed overload
    : LiteralKit<FilterTuple<L, O[number]>>
}
```

`FilterTuple` (order-preserving tuple filter) is a modest recursive conditional — far cheaper than the pre-trim `ValidEnumMapping` validator chain (pre-trim :89-123) because it never has to prove coverage of a user mapping, only subtract from a fixed tuple.

## 2. Naming

My preferences, in descending order of confidence:

- **`Enum` — keep.** Yes, it shadows the TS `enum` keyword conceptually; no, that is not a practical problem in a codebase that has banned nothing here and reads `Status.Enum.hello` fluently across 227+ files. Zod independently converged on `.enum` for exactly this artefact ([zod.dev/api](https://zod.dev/api?id=enums)). Renaming to `values`/`members` would collide with upstream `members` (`Schema.d.ts:4140-4142`, which are *schemas*, not values — a worse collision).
- **Guards: rename `is` → `guards`? I lean keep `is`, reluctantly.** Upstream Schema's own spelling for the record-of-guards on tagged unions is `guards` (`Schema.d.ts:5179-5181`, `:5290-5292`), and the upstream tagged-union augmentation proposal (Effect-TS/effect-smol#113) used `is` for the same artefact. Two upstream precedents disagree. I keep `is` for one reason: `Status.is.hello(x)` reads as a predicate at the call site, whereas `Status.guards.hello(x)` reads as plumbing. But I flag this as my least-firm naming call (§ "Where I am unsure"). Whatever is chosen, the *members* of the record should be keyed identically to `Enum` — that invariant matters more than the record's name.
- **Match: drop the `$`. Call it `match`.** The `$` prefix in Effect means exactly one thing: the `Data.taggedEnum` bundle (`$is`, `$match` at `Data.d.ts:365-379`), where `$` disambiguates helpers from *user variant constructors* sharing the same object. A `LiteralKit` has no constructors in that namespace, so the disambiguation buys nothing and costs consistency with `Schema.TaggedUnion.match`/`matchOrElse` (`Schema.d.ts:5293-5308`) and `TaggedUnionUtils.match` (`Schema.d.ts:5182-5189`), both dollar-free. The current code even acknowledges the debt by naming the exported helper `matchLiteral` (`LiteralKit.schema.ts:164`) while the member is `$match`. Reasonable people will disagree — `Data.taggedEnum` parity is a real argument for a repo that destructures both — but I lean `match` (with `matchOrElse`, §3) because Schema, not Data, is this kit's parent abstraction; the kit *is* a Schema. Migration cost is a codemod the repo demonstrably knows how to write (`SchemaParityCodemodLiteralKitRule.ts`). If the rename is judged too churny for 352 `$match(` sites, keeping `$match` is defensible; keeping it *because* `taggedEnum` does is not.
- **`toTaggedUnion` — keep the name.** It matches upstream's free function `Schema.toTaggedUnion` (`Schema.d.ts:5253`) exactly, which is the correct precedent for a schema-to-schema conversion. Good call in the current code.
- **Subset verbs: `pick` and `omit`, matching upstream `pick`.** Upstream chose `pick` (`Schema.d.ts:4147`); Zod chose `extract`/`exclude` for the same pair. I follow upstream: symmetry with the method consumers already call, and `omit` is the established complement name in TS utility-type vocabulary (`Omit`). The pre-trim `pickOptions`/`omitOptions` names were worse — noun-suffixed, and they returned *option tuples*, a different artefact from a kit.
- **`LiteralToKey` / `matchLiteral` — keep.** The key-mangling scheme (`number200`, `bigint20n`, `true`) is ugly and necessary: JS object keys are strings, and mixed literal domains need injective keys. The constructor already throws `LiteralKitKeyCollisionError` on genuine collisions (`LiteralKit.schema.ts:246-272`). I would *not* expose `matchLiteral` as public API beyond its current export — it is an implementation detail of the key scheme that consumers should never call directly; but since it is exported and tested, deprecating it is a separate conversation.

No helper should use a `$` prefix in my surface except, possibly, a future destructure-bundle deliberately mirroring `Data.taggedEnum`. None is proposed.

## 3. Exhaustiveness

**Yes: the record match is exhaustive by default, and there should be no non-exhaustive record form on the kit.** The current implementation gets this right: `MatchCases` requires every key (`LiteralKit.schema.ts:65-67`) and rejects unknown keys via the `Exclude<keyof Cases, MatchKeys<L>>: never` trick (:85, :89), and the runtime comment "exhaustive by construction" (:285, :290) is accurate because the input type is the closed union `L[number]`. An unmatched value is therefore *unrepresentable* for well-typed callers; for ill-typed (cast) callers the current code does `cases[key]!(value)` (:286), which will throw a raw `TypeError` on a missing handler. That is acceptable but improvable: throw the kit's own descriptive error (or `Match`'s absurd-style failure) naming the value and domain, since a cast-driven miss is exactly when a bare `undefined is not a function` wastes debugging time.

Non-exhaustive matching is a different need — "handle these members, default the rest" — and it already has two good homes that should *not* be duplicated on the kit:

1. `matchOrElse(cases, orElse)` if the kit wants the record form with a fallback — I would add this, mirroring upstream `TaggedUnionUtils.matchOrElse` (`Schema.d.ts:5190-5205`) and `TaggedUnion.matchOrElse` (`Schema.d.ts:5301-5308`), with partial cases typed `Partial<MatchCases<L>>` and `orElse: (value: L[number]) => R`. This is the one addition to the match family I endorse.
2. `effect/Match` chains (§4) for predicate-rich, multi-step matching where the record form is the wrong tool.

What I would *not* add: an `Option`-returning match or a "partial match that returns `undefined`". Silent `undefined` on an unmatched member of a closed domain is how exhaustive domains quietly become partial ones. If a caller wants fallibility, `matchOrElse` with an explicit handler makes the default visible in the types.

One refinement to the current typing: both overloads require the *full* `MatchCases` even in the curried form. That is correct. But the excess-key guard (`& { [K in Exclude<...>]: never }`) produces notoriously unreadable errors when a member is renamed. A dedicated "unknown case" error message is not achievable in pure TS types; I accept the cost, but the JSDoc should show a rename example so the error is recognisable when it fires.

## 4. `effect/Match` interoperability

**Yes, but as a bridge to `Match.tags`-style record handling for bare literals, not as a re-implementation of the pipeline.** The gap is real and specific: `Match` can match bare literal *values* only one pattern at a time (`Match.when("repair-loop", ...)` at `Fold.ts:304-310`, ending in `Match.exhaustive`), and its record forms (`tags`, `tagsExhaustive`, `valueTags`) all require a `_tag` field (`Match.d.ts:1073-1115`, `:390-457`). The 2026-09-15 ruling already noted this: "`Match` has `valueTags` for tagged values only" (`DECISIONS.md:459`). Meanwhile `Fold.ts:298-313` shows a real consumer hand-rolling a `Match.type<...>().pipe(Match.when ×4, Match.exhaustive)` chain over a domain that *is* a `LiteralKit` (`KpiTier`, `Schemas.ts:48-55`) — the record form would be shorter and the exhaustiveness would be checked against the domain rather than restated.

The shape I would add is a *matcher combinator* that slots into an existing chain, named to parallel `Match.tagsExhaustive`:

```ts
// on the kit
valuesExhaustive<const Cases extends MatchCases<L>>(
  cases: Cases
): <I, F, R, A, Pr, Ret, Args extends Array<any>>(
  self: Match.Matcher<I, F, R, A, Pr, Ret, Args>
) => (value: L[number]) => Unify.Unify<MatchReturn<Cases>>
```

Honestly, though, the *cleaner* design is not a kit method at all: it is a standalone combinator in `@beep/schema` (or upstream, §6) that takes the kit (or any `Literals`) as its dictionary:

```ts
MatchLiterals.valuesExhaustive(KpiTier, { "repair-green": ..., /* ... */ })
```

I lean toward the standalone combinator for three reasons: (1) it keeps the kit's instance surface to value-level helpers and keeps `effect/Match`'s `Matcher` type machinery out of the kit's interface file; (2) it composes in both directions — inside a `pipe` chain *and* standalone — without overloading the kit with pipeline-aware overloads; (3) interaction with `Match.withReturnType` (`Match.d.ts:639`) and `Match.exhaustive` (`Match.d.ts:1953`) stays upstream's problem: the combinator should be usable *instead of* the terminal `exhaustive` (it is itself exhaustive) and should respect a prior `withReturnType` by unifying case returns the same way `tagsExhaustive` does (`Match.d.ts:1113-1115` returns `Unify<A | ReturnType<...>>` when a return type was preset). If the combinator cannot see the `Pr` (preset-return) parameter cleanly, the fallback is to document "use as the terminal step; do not follow with `Match.exhaustive`" — which is precisely how `tagsExhaustive` behaves.

What I would *not* do: make `$match`/`match` itself return a `Matcher`, or add `when`-style single-case methods to the kit. The kit's record match is a closed-domain fold; `Match` is an open pipeline. Bridging them at exactly one point (record → pipeline step) serves both; merging them serves neither.

## 5. Implementation quality

The current implementation is better than the pre-trim one in the way that matters most, and still wasteful in ways worth fixing.

**What the trim fixed — keep it.** Replacing the `annotate`-only wrapper (pre-trim :608-626) with a `rebuild` override (`LiteralKit.schema.ts:304-318`) is the correct mechanism: upstream `annotate`/`annotateKey`/`check` all funnel through `this.rebuild(ast)`, so one override re-attaches statics across every derivation, including the `.pipe($I.annoteSchema(...))` at `Schemas.ts:55-59` and the `S.check(...)` pipe in the tests (`LiteralKit.test.ts`, `PipedDirection`). The type-cost numbers in the trim commit are the strongest evidence in this whole history: single-checker instantiations dropped by 51,729 (`@beep/schema`), 18,209 (repo-cli) and 29,512 (law-practice-domain) when the `M` parameter and its validators (pre-trim :89-123, :482-552) were deleted. Any proposal of mine must be held to that bar: kit-preserving `pick`/`omit` adds one mapped/conditional type each, orders of magnitude less than `ValidEnumMapping`.

**Runtime cost today.** Every kit construction eagerly builds: the `Enum` record via a spreading reduce (`LiteralKit.schema.ts:173-177` — `A.reduce` with `{...acc, [k]: v}` is O(n²) property copies and allocates n intermediate objects), the guards record the same way (:179-183, one closure per member), a fresh `HashMap` walk for collision detection (:262-272), and the `$match` closure. For the repo's typical n (2–12) this is noise; for `OfficeCode`-scale kits (~240 members, `CitingApplicationIdentity.model.ts:82`) it is 240 closures + a quadratic record build at module load, multiplied across ~600 kit constructions at import time. Concrete improvements, in order:

1. **Build records with a single mutation loop, not spreading reduce.** `const out: Record<string, unknown> = {}; for (const lit of literals) out[matchLiteral(lit)] = lit;` — O(n), one allocation, identical frozen result. The current `makeEnum`/`makeGuards` (and `MappedLiteralKit`'s `makeForwardEnum`/`makeReverseEnum`, `MappedLiteralKit.schema.ts:127-143`) all pay the quadratic spread. This is a strict improvement with no trade-off.
2. **Make `is` guards share one implementation.** Every guard is `(i) => i === literal` with a captured literal — fine — but they can be built from the `Enum` record in the same loop instead of a second reduce. Minor; do it while fixing (1).
3. **Skip the collision `HashMap` for the overwhelmingly common case.** `assertUniqueHelperKeys` (:262-272) allocates a `HashMap` and re-derives every key via `matchLiteral`, which itself runs a `Match.value(...).pipe(Match.when ×4, Match.orElseAbsurd)` pipeline (`LiteralKit.schema.ts:164-171`) *per literal per construction*. That is the real hot spot: `matchLiteral` is called by `makeEnum`, `makeGuards`, `buildMatch` (per invocation), `toTaggedUnion`, *and* the validator, each time spinning up a `Matcher`. Replace `matchLiteral`'s body with a plain `typeof` dispatch (`typeof literal === "boolean" ? ... : ...`). Same semantics, no pipeline allocation, and the function becomes cheap enough to call everywhere. Using `Match` to implement a four-way `typeof` switch inside the kit that exists partly to *avoid* verbose `Match` chains is an irony the code can live without.
4. **Lazily compute the derived set (if §1's lazy `HashSet` is adopted)** via a memoised getter descriptor instead of the pre-trim eager `HashSet.fromIterable(literals)` (pre-trim :826). Non-enumerable, computed on first access, one instance per kit. Do *not* make `Enum`/`is` lazy: they are the primary API and are accessed at module scope by consumers (`X.Enum.k` in default parameters), so deferring them only moves the cost, and lazy enumerable getters complicate the `Object.defineProperties` descriptor story (:442-447) and snapshot tests that assert descriptor shape (`LiteralKit.test.ts` "defines helper properties as readonly").
5. **`toTaggedUnion` is already appropriately lazy** — the closure captures `base` and only runs `mapMembers` when invoked (:416-440) — but it re-checks `P.isPropertyKey` per member per call; hoist the key computation. Trivial.

**Statics through derivations.** The `rebuild` override (:307-317) is sound, but note its subtlety: it captures the *original* `descriptors` map, so a kit derived twice still carries the first kit's `Enum` — correct here because derivations (`check`, `annotate`) do not change the literal set. The danger case is `pick`: upstream `pick` is a method on `Literals` that constructs a *new* `Literals` from the subset, which under my §1 proposal must construct a *new kit* with subset descriptors, not re-attach the parent's. That is precisely why kit-preserving `pick`/`omit` should be implemented as fresh `LiteralKit(subset)` constructions (reusing the constructor, collision check included) rather than as descriptor tricks. Cost: one extra construction per subset derivation, at module scope. Acceptable, and it keeps the invariant "a kit's helpers always describe its own `literals`" trivially true.

`MappedLiteralKit` has the same descriptor machinery duplicated (`MappedLiteralKit.schema.ts:203-220`) with a `makeDescriptors` callback — and a real wart: each directional kit constructs a full inner `LiteralKit(from)` (`MappedLiteralKit.schema.ts:232`) purely to borrow its `is`/`$match`, throwing away its `Enum` and paying a second collision validation. Extract the record builders (`makeEnum`/`makeGuards`/`buildMatch`) into shared internal functions and have both kits use them; the directional kit needs guards/match *of the from-side* with the *mapped* `Enum`, which is exactly a parameterisation the pre-trim code had and the trim removed along with `enumMapping`. Sharing builders recovers that without re-adding the `M` type parameter to the public `LiteralKit` (the mapping lives in `MappedLiteralKit`'s types, where it belongs).

**Bundle size.** The kit imports `effect/HashMap`, `effect/Option`, `effect/Match`, `effect/Predicate` (`LiteralKit.schema.ts:10-14`) largely for the validator and `matchLiteral`. Change (3) above drops the `Match` import; the validator can use a plain `Set`-free loop with `Object.is` over the literals array (repo law mandates `HashSet`/`HashMap` over native `Set`/`Map` in *Effect-facing* code, but for an internal n≤240 uniqueness scan a simple nested `Object.is` comparison is O(n²) worst-case yet allocation-free and dependency-free — or keep `HashMap` if the law is read strictly; the allocation is once per construction either way). Net: the kit's marginal bundle cost is already small; the win is construction-time CPU, not bytes.

**Type-level cost.** Current machinery is lean: three mapped types (`EnumType`, `IsGuards`, `MatchCases`, :57-67), one distribute-over-union for tagged members (:113-132), `const` type parameters throughout (`LiteralKit` constructor :412). Two cautions: (a) `MatchReturn`'s infer-per-key mapped type (:79-81) plus `Unify.Unify` is the standard upstream idiom (`Data.d.ts:373` does the same), keep it; (b) the tagged-union member computation distributes `Literal extends L[number]` (:118-122) which is O(n) instantiations of `S.Struct<...>` — the typeperf fixture exists because this is the kit's most expensive type. My `omit`'s `FilterTuple` must be tail-recursive and operate on the tuple, not distribute over the union, to avoid compounding that cost on subset derivations.

## 6. Upstream

Part of this belongs in Effect; part emphatically does not.

**Belongs upstream (in `Schema.Literals` or `Schema` generally):**

- A kit-preserving subset algebra is *not* upstream's business in kit form — but the underlying gap is: upstream `Literals.pick` returns `Literals<L2>` (`Schema.d.ts:4147`) and there is no complement. A `Literals.omit` (or `exclude`) upstream, returning `Literals<Complement>`, is a small, obvious completion of the existing pair — Zod has exactly `extract`/`exclude` on enums, Valibot has `picklist` + union helpers. I would propose `omit` upstream before proposing anything else.
- Record-form exhaustive matching and per-member guards **for tagged unions already landed upstream in spirit**: `TaggedUnionUtils` has `guards`/`match`/`matchOrElse` (`Schema.d.ts:5179-5205`), and effect-smol#113 shows the team accepted augmenting unions with `is`/`match` keyed by tag. Extending the same treatment to *bare literal unions* — e.g. `Schema.Literals` gaining `guards` and `match` keyed by `LiteralToKey`-style stringification — is a coherent upstream feature request, and the stringification rules (how `200` and `"200"` coexist as keys) are exactly the kind of decision that should be made once, upstream, rather than per-repo. The repo's `LiteralToKey` (`LiteralKit.schema.ts:47-55`) is a good concrete proposal to bring.
- The `Match` bridge (§4): a `Match.values`/`valuesExhaustive` for bare literal unions is upstream-shaped; `Match` already special-cases `_tag` records three times over (`tags`, `tagsExhaustive`, `valueTags`).

**Stays repo-local:**

- The *domain-kit packaging* — one constructor that returns schema + keyed API as a single named artefact, with statics surviving `check`/`annotate` via `rebuild`. That is an opinion about how *this* codebase names domains (code law: "LiteralKit stays the default for named literal domains", per `DECISIONS.md:495-498`). Upstream deliberately keeps `Schema` combinators orthogonal and composable; a pre-bundled kit is a repo convention, like `MappedLiteralKit` (reversible wire mappings are a law-practice-shaped need upstream should never hear about).
- The collision-error policy (throw a `TaggedError` at construction). Upstream would more likely make key derivation total or document the collision; the repo's fail-fast with a domain error is a local taste I endorse locally.

Honest caveat: upstreaming the keyed helpers would take a release cycle this repo (on pkg.pr.new snapshots) might actually influence, but the repo should not *wait* for it. Ship locally, propose upstream, delete locally if accepted — that is the doctrine working as intended (`standards/architecture/DECISIONS.md:2030-2038`).

## 7. Existence

**Yes, the kit should exist — and the strongest argument is not the 600 files, it is what those files would become without it.** The counterfactual is visible in miniature wherever the kit is *not* used: `Fold.ts:298-313` hand-maintains a `Match.type<...>().pipe(Match.when ×4, Match.exhaustive)` chain whose handled set must be kept in sync with `KpiTier` by hand, and `CitingApplicationIdentity.model.ts:82-318` hand-maintains 236 literals that must stay the complement of another list by hand. Multiply that discipline across 227 files of `.Enum` references and 259 of `.is` guards and the kit is not saving keystrokes — it is the single place where "these strings are one closed domain" is *said once* and then enforced by the compiler everywhere else. That is schema-first design as this repo practises it: the literal tuple is the model, and `Enum`/`is`/`match` are its derived views. Plain `Schema.Literals` gives you the model and none of the views.

The uncomfortable version of the argument deserves stating plainly, because it is the best case against: the kit is a *second* pattern-matching and guard system next to `effect/Match` and `Schema.TaggedUnion`, with its own key-mangling scheme, its own error classes, and a `rebuild`-override hack to survive the upstream class hierarchy. Every Effect bump must re-audit it (the doctrine says so), and its existence teaches newcomers a repo dialect (`Status.Enum.number1`) that does not transfer. If the repo were starting today with today's upstream — `TaggedUnionUtils.guards/match`, `Match.tagsExhaustive`, `Literals.pick` — I would still build it, but I would build it at about two-thirds of its historical size: schema + `Enum` + guards + exhaustive record match + `toTaggedUnion` + kit-preserving subsets, nothing else, which is close to what I propose in §1. The trim got the kit to roughly that size; my disagreement is at the margins (subsets, naming, laziness), not the core.

What would change my mind: upstream shipping keyed `guards`/`match` on `Schema.Literals` itself. At that point the kit's remaining unique value is `Enum` and the subset algebra, and the honest move is the doctrine's own ADAPT/RETIRE census again. Until then, deleting this kit to save maintaining ~450 lines, at the cost of degrading 2,000+ consumer lines into hand-synced duplicates, is a bad trade by the repo's own stated metric (`DECISIONS.md:511-517`).

## Where I am unsure

- **`is` vs `guards` for the guard record.** Upstream Schema says `guards`; upstream `Data.taggedEnum` and the smol augmentation proposal say `$is`/`is`; call-site readability says `is`. I keep `is`, but a maintainer who weights upstream-Schema consistency over readability could flip me — this is a coin I have weighted, not a fact I have established.
- **Whether kit-preserving `pick` should override upstream `pick` or get a distinct name.** Overriding changes the return type of an inherited method (still a `Literals`, so substitutable, but the *runtime object* gains properties — usually benign, occasionally surprising under `deepStrictEqual`-style tests; the kit's own test at `LiteralKit.test.ts` "derives subsets through upstream pick" asserts only `.literals`). A separate name (e.g. `subset`) avoids the surprise but forks the vocabulary. I lean override; I am not certain.
- **The lazy `HashSet`.** My "lazy memoised getter" compromise depends on how often membership tests against a kit actually occur in hot paths, which I censused only anecdotally (test files rebuilding `HashSet.fromIterable(X.literals)` per call). If real production hot paths exist, an eager set is justified; if none do, even the lazy getter is speculative surface. I hold "lazy or nothing" loosely.
- **The `Match` bridge shape.** Whether `Matcher`'s `Pr` preset-return parameter can be threaded so the combinator honours a prior `Match.withReturnType` needs a prototype against `Match.d.ts:639,1113-1115`; I have specified the desired behaviour, not verified the typing compiles at reasonable instantiation cost.
- **Instantiation cost of my `omit` on very large kits.** `OfficeCode`-scale domains (~240 members) are where a tuple-filter conditional could hurt; I have argued it is cheaper than the deleted `ValidEnumMapping`, but I have not measured it. The typeperf fixture pattern (`test/fixtures/typeperf/`) is where this should be proven before adoption.

## Disagreements with the current code or its history

1. **The trim's treatment of `omit` was wrong, and its own rationale contains the refutation.** "Omit becomes an explicit pick of the complement at its 13 sites" (`DECISIONS.md:470-472`) optimises for the day of the migration and pessimises every domain edit after it. Evidence: `CitingApplicationIdentity.model.ts:80-318` now spells out 236 literals as a "complement pick", with a comment admitting the workaround and an explicit type argument to tame inference. A complement that must be hand-maintained is not a complement. This facet should be restored as a computed, kit-preserving `omit` (§1).
2. **Judging `pick` "covered" by upstream ignored that derivations lose the kit.** The census counted construction and `.pick` as upstream-covered (`standards/architecture/DECISIONS.md:2078-2082`) without asking what consumers do *next* with the subset. What they do next is `LiteralKit(X.pick([...]).literals)` — 11 current sites re-wrap the subset to get their helpers back. Coverage that requires immediate re-wrapping is not coverage; the doctrine's facet test (`standards/architecture/DECISIONS.md:2040-2045`) should be amended to require that the covered API survive the derivation consumers actually perform.
3. **`matchLiteral` is implemented with a full `Match` pipeline for a `typeof` dispatch** (`LiteralKit.schema.ts:164-171`), and it sits on the construction path of every kit (via the collision validator, `makeEnum`, `makeGuards`). This is the kind of internal extravagance the Upstream-First doctrine exists to prevent, one level down: using the heaviest available machinery for the simplest job, at the most-executed moment.
4. **Quadratic record construction.** `makeEnum`/`makeGuards` (current :173-183) and `MappedLiteralKit`'s enum builders (`MappedLiteralKit.schema.ts:127-143`) build records by spreading an accumulator — O(n²) copies, n intermediate objects, per kit, at module load. For a helper whose entire selling point is cheap derived views, the derivations should be built with a single mutation loop.
5. **`MappedLiteralKit` builds a throwaway `LiteralKit` per direction to borrow two of its facets** (`MappedLiteralKit.schema.ts:232`, used at :240-244), paying double construction and validating collisions twice, because the shared builders were deleted with `enumMapping` instead of being factored out. The trim removed a public type parameter (good) and, in doing so, removed the internal parameterisation that a sibling kit legitimately needed (bad). Factor the builders; don't re-add the parameter.
6. **The `$` in `$match` (and `$is` in `Data`-style naming generally) was copied from a context where it solves a problem this kit does not have.** `Data.taggedEnum` needs `$is`/`$match` because variant constructors share its namespace (`Data.d.ts:358-380`). A `LiteralKit` has no constructors; the `$` is pure signalling debt, inconsistent with `Schema.TaggedUnion.match` (`Schema.d.ts:5293`). I would rename to `match`/`matchOrElse` at the next codemod opportunity. (Noted as a lean, not a certainty — 352 call sites of churn is a real cost, and the codemod to do it already exists in embryo.)
7. **The 2026-09-14 "LiteralKit retires; its helpers are ergonomics" ruling** (superseded at `DECISIONS.md:518-525`) was decided on the schema facet before the consumer census existed. The 09-15 correction handled it well, but the episode should be recorded as a methodological error, not just a superseded entry: a retirement judged without a static-facet census nearly deleted the most-used API in the package. The doctrine now requires the census over 100 consumers (`standards/architecture/DECISIONS.md:2046-2048`) — good — and I would extend the same requirement to *facet* retirements over 100 consumers, which is the gap the `omit` decision (item 1) fell through: 13 sites is under the threshold, yet the facet's value was never in its site count.
