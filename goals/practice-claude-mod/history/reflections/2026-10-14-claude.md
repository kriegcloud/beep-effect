# Reflection — practice-claude-mod (2026-10-14, claude)

## Summary

The goal shipped the `oip-practice` Claude Code plugin for the attorney's sessions in three PRs (#1730 rows and verdicts, #1756 matter band, visible timer and five firm skills, and the closeout PR with the shared-envelope promotion). It is installed from a local directory marketplace on the attorney's Windows PC and answers headless commands there. The review-queue phase (P1b) moves to a gated follow-on, because its entry gate is a separate goal's spikes and schema.

## Tooling experience

- **Worked:** the mods engine test kit (`claude plugin test`) caught behaviour that unit tests could not (bottom hooks for `mcp.call`, `session.id`, toasts); Codex lanes for the engine-contract read, gate repair, the matter/timer slice, the skill port and the promotion kept main-thread context small; the cache-baseline request flow and package gates were precise once known.
- **Didn't:** the Codex workspace-write sandbox cannot run `claude plugin test` in aggregate or bun vitest fork workers, so every lane's "fail" there had to be re-run in the owning session.
- **Frustrating:** the mod validator's static rules (see findings); new-package governance gates arriving one per publish (cache policy, then knip/fallow/effect-vitest, then JSDoc ratchet, then the identity registry formatting).
- **Wished existed:** a "new package preflight" that runs every governance gate a first publish of an app will hit, and a mod scaffold for Effect-bundled hooks.

- **MEDIUM — Best practice:** build mod evidence on the operator machine with a copy of the practice-kg bundle; the live bundle is held open by the always-on docket-intake service.
